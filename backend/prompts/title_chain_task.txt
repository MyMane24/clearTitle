## Field rules

- Order: `title_chain` and the graph both run chronologically from the earliest
  supported root to the current owner. `chain_position` is 1, 2, 3 and so on.
- Identity: never output a `tx_id` or any transaction identifier. The application
  assigns stable IDs and upstream links when it saves.
- Evidence only: fill each field from what the cited evidence states and leave it
  null when absent. Record parties exactly as the instrument writes them, one
  entry per named party, `[]` for an unstated list, never a guess. Parties must
  agree with `summary_points`. For a recital-only link, record the reported
  names as stated and set `evidence_status` to `recital_reported`, with null for
  unavailable dates and instrument numbers.
- Property fields: `property_type` is a short label (two to four words) for the kind
  of property this link transfers, set per link so that a change of type (land
  to plot to house or flat) is visible in the chain. `property_schedule` is the
  schedule wording. `survey_number`, `plot_number`, `site_flat_number` and
  `cts_number` each hold only the bare identifier as written ("699A/15", "9",
  "G-04", "1360B/9"), never a description such as "Open site Plot No.9", and
  never the same value in two fields. Descriptions belong in `property_type` and
  `property_schedule`.
- `transaction_number`: only an explicit registration or instrument number. Keep
  provenance notes ("EC entry", "instrument not supplied", "reported in EC") out
  of `transaction_type`; provenance lives in `evidence_status` and `source_refs`.
- `summary_points`: plain-language sentences, one fact each, with no field labels
  such as "Seller:" and no filenames or source references. State the parties and
  their roles, the property or schedule, important terms, consideration when
  stated, and material events or discrepancies. Use a short numbered list inside
  one point only for a long list of people. Do not repeat the graph or the
  property identity.
- `source_refs`: `doc_id` and `filename` only, at transaction or event level. The
  filename must match the uploaded filename exactly.
- `related_events`: for each period between ownership links, include relevant
  property events found in the uploads (conversion orders, mortgages,
  construction or allocation records, permissions) with their dates; leave out
  unrelated records.
- Do not add an `unresolved` field to `property_identity` or any chain entry, and
  do not add a title story or chain summary field.
- Keep the result compact enough for a single valid tool call. Leave out raw OCR,
  long quotations, unsupported events and unknown document IDs, and keep
  transaction details that already appear in `title_chain` out of the graph.
